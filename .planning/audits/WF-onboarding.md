# WF-onboarding — Onboarding Workflow Audit

**Lens:** How a brand-new user gets rcode onto an existing project and reaches their first useful action.
**Auditor date:** 2026-09-16

---

## Verdict

The install mechanics are solid — one `pnpm dlx` command ships ~300 files correctly — but the post-install path is broken in two distinct ways: the shell output tells users to run `/rcode-progress` first while every doc says `/rcode-init` is mandatory, and a structural flaw in the seeded-config marker means every new user is asked 4–5 setup questions **twice** (once in the install wizard, again in the auto-init-guard when they run their first command). The "first 5 minutes" path is leaky enough that most users will end up with unscanned project context, silently degraded agent responses, and lingering confusion about which command they were supposed to run first.

---

## The user's actual experience

### Step 1 — Install (`cli/install.js`)

User runs:
```bash
pnpm dlx @hanzlaa/rcode install
```

The interactive wizard (`runInstallWizard`, `cli/install.js:1738`) asks 6 questions:
1. Install directory (if not provided)
2. Editor/LLM (multiselect: Claude Code, Cursor, Codex, Gemini, VS Code, Antigravity)
3. Communication language
4. Agent mode (guided/yolo)
5. Planning artifacts (commit to git / keep local)
6. User name

After wizard completes, install writes:
- `.rcode/config.yaml` — with the comment `# Generated by install. Safe to edit.` on line 2 (`cli/lib/install-config.cjs:51`)
- `.rcode/state.json` — with `"_seeded_stub": true` (`cli/install.js:847`)
- `.rcode/context/active.md` — stub: `_Run `/rcode-init` inside your AI editor to populate this file._` (`cli/install.js:880`)
- `.rcode/context/project-brief.md` — same stub (`cli/install.js:883`)
- `CLAUDE.md` — with only the `/rcode-do` rule block appended (`cli/lib/install-hooks.cjs:400`)
- `.claude/agents/`, `.claude/commands/rcode/`, `.claude/skills/` — all 45 agents, 117 commands, 96 skills

**NOT written by install:** `.rcode/JOURNEY.md`

### Step 2 — The "Next:" output and the fork in the road

The installer prints (`cli/install.js:1101–1106`):
```
  Next:
    cd {target}
    claude              # start Claude Code (reload window if already open)
    /rcode-progress     # where you are, what's next
    /rcode-do           # interactive command picker
    /rcode-council <q>  # multi-agent strategic answer
```

`/rcode-init` is **not listed here**.

Meanwhile:
- `docs/getting-started.md:27` says: "`/rcode-init` is **the** first command — always run this one, never anything else to start."
- `README.md:176` says: `# 2. Restart Claude Code, then: /rcode-init`

User is immediately split between two incompatible first-command instructions.

### Step 3 — First command fires the auto-init-guard

Whether the user follows the installer (`/rcode-progress`) or the docs (`/rcode-init`):

**Path A — user runs `/rcode-progress`:**
`rcode/workflows/status.md:10` loads `@.rcode/references/auto-init-guard.md`. The guard runs:
```bash
if grep -q "Generated by install" .rcode/config.yaml 2>/dev/null && [ ! -f .rcode/JOURNEY.md ]; then
  echo "rcode-seeded-not-configured"
```
This fires **every time after a fresh install** because:
1. `# Generated by install.` is always written to config.yaml (`cli/lib/install-config.cjs:51`)
2. JOURNEY.md is never written by install (confirmed: no reference in `cli/install.js`)

Result: auto-init-guard intercepts and asks the user the 5 config questions **again** (`auto-init-guard.md:63–72`): name, language, mode, model_profile, commit_planning. The user already answered name, language, mode, and commit_planning in the install wizard. Only model_profile is new.

**Path B — user runs `/rcode-init`:**
`rcode/workflows/init.md` also checks for `_seeded_stub: true` (`rcode/workflows/init.md:47–50`), classifies state as `existing-new-rcode`, and asks the same 5 questions in Step 2 (`rcode/workflows/init.md:118–130`). Again, 4 of 5 were just answered in the install wizard.

### Step 4 — What `rcode-seeded-not-configured` actually does (auto-init-guard path)

The inline init flow (auto-init-guard.md:31–123):
1. Skips bin bootstrap (already done)
2. Asks 5 config questions
3. Writes `.rcode/config.yaml` — overwrites install-seeded version with real answers
4. Seeds `.rcode/state.json` and `.planning/` structure
5. Writes stub context files: `active.md` and `project-brief.md` with `_Run /rcode-init for full setup._`
6. Says "Continuing with your original request..."

**Critically:** the auto-init-guard inline flow does NOT:
- Write JOURNEY.md
- Scan the codebase
- Populate the real `active.md` or `project-brief.md` with project context

So after auto-init-guard runs inline, context files still contain `_Run /rcode-init for full setup._`. Any of the 124 workflows that do NOT include the auto-init-guard (`rcode/workflows/add-phase.md`, `rcode/workflows/dev-story.md`, `rcode/workflows/audit.md`, etc.) will run against stub context.

### Step 5 — What the user can actually DO

After auto-init-guard completes inline OR after `/rcode-init` completes (with codebase scan):
- `/rcode-council <question>` — works, but agents read `active.md` (stub until /rcode-init scans)
- `/rcode-status` — works, shows empty/seeded state
- `/rcode-scan` or `/rcode-discuss` — works

The first truly useful action for an existing project is `/rcode-scan` or `/rcode-council` after the scan context is populated. That requires completing `/rcode-init` (full path, not auto-init-guard inline path).

## Leaks

1. **🔴 Install "Next:" steps contradict every doc** — `cli/install.js:1103–1106` lists `/rcode-progress` as the first command. `docs/getting-started.md:27` says `/rcode-init` is "the first command — always run this one, never anything else to start." `README.md:176` also says `/rcode-init`. A new user who follows the installer's own output walks a path the docs say is wrong. **User cost:** confusion, loss of trust, unpredictable first session.

2. **🔴 Every post-install session asks redundant setup questions** — `cli/lib/install-config.cjs:51` writes `# Generated by install.` unconditionally, and install never writes `JOURNEY.md`. The auto-init-guard detection condition (`auto-init-guard.md:14`) therefore always fires `rcode-seeded-not-configured` on first command after install. The user re-answers name, language, mode, and commit_planning — all of which were captured in the install wizard. **User cost:** 4 duplicate questions; erodes confidence; model_profile being the only net-new question buries the value of the init flow.

3. **🔴 124 of 131 workflows run blind on stub context** — install writes `_Run /rcode-init inside your AI editor to populate this file._` to both `active.md` and `project-brief.md` (`cli/install.js:880,883`). Only 7 workflows include the auto-init-guard (`council`, `do`, `execute`, `init`, `new-project`, `plan`, `status`). The other 124 (`add-phase`, `dev-story`, `audit`, `brainstorm`, `code-review`, etc.) read context files and get the stub placeholder. **User cost:** agents silently produce context-free output; the user doesn't know why their first `/rcode-add-phase` ignores everything about the project.

4. **🟡 getting-started.md describes 3 wrong questions** — `docs/getting-started.md:28–31` lists "Is this a new or existing project?", "What's your preferred communication language?", "What's your model profile?" as the 3 questions `/rcode-init` asks. The actual init workflow asks 5 questions (name, language, mode, model_profile, branching_strategy — `rcode/workflows/init.md:118–130`), and "new or existing project" is auto-detected, not asked. **User cost:** user arrives at `/rcode-init` expecting 3 questions, gets 5, and the questions are different — breaks mental model.

5. **🟡 Version drift across docs** — `docs/install.md:4` says current version is `v4.4.4 (2026-06-27)`. `README.md:26` says `v4.9.0`. `package.json` says `v4.17.0`. **User cost:** users don't know what version they're actually installing; changelog links are useless if they're looking at the wrong release.

6. **🟢 IDE restart is soft-pedaled** — `docs/getting-started.md` says "Restart your IDE" in the Install section but doesn't make it explicit that commands won't appear at all until restart. `cli/install.js:1130` prints a warning only, and only when IDE is already open. `README.md:175–176` says "Restart Claude Code" but buries it. **User cost:** user opens Claude Code mid-install, types `/rcode`, sees nothing, thinks install failed — abandons before trying restart.

## Strengthenings

**1. Remove `/rcode-init` from the first-command path entirely — auto-init the config at install time (M)**
The install wizard already captures name, language, mode, and commit_planning. After wizard completes, strip the `# Generated by install.` marker from the written config.yaml (or omit it when wizard ran) and seed a minimal JOURNEY.md stub. This eliminates the `rcode-seeded-not-configured` detection branch entirely for wizard-run installs. Files: `cli/install.js`, `cli/lib/install-config.cjs`. The auto-init-guard retains its value for `pnpm dlx @hanzlaa/rcode install --yes` (non-interactive) where no questions were asked.

**2. Add `/rcode-init` to the install "Next:" output as the mandatory first step (S)**
`cli/install.js:1101–1106` should list `/rcode-init` first, not `/rcode-progress`. The current order (`/rcode-progress`, `/rcode-do`, `/rcode-council`) assumes a configured project. One line change: replace the `/rcode-progress` entry with `/rcode-init` and move `/rcode-progress` to second. Files: `cli/install.js:1104`.

**3. Populate real context files from install wizard data (S)**
After the wizard captures name, project_name, and mode, write a non-stub `active.md` with at minimum the project name, stack detection (from `ls package.json pyproject.toml`), and wizard answers. The stub `_Run /rcode-init for full setup._` text means the first 124 workflows that run without init operate blind. Even a 3-line real context (project name, date, "run /rcode-init for full codebase scan") is better than a placeholder instruction. Files: `cli/install.js:877–883`.

**4. Fix getting-started.md to match actual init questions (S)**
`docs/getting-started.md:28–31` lists 3 questions that don't match the 5 that `/rcode-init` actually asks. Rewrite to match `rcode/workflows/init.md:118–130`. Also remove "Is this a new or existing project?" — this is auto-detected, not asked. Files: `docs/getting-started.md:27–31`.

**5. Pin version in docs to a generation mechanism, not a hardcoded string (M)**
`docs/install.md:4` is out of date by 13 minor versions. Use a docs-generation step that reads `package.json` version into the markdown, or replace the hardcoded string with a badge. Files: `docs/install.md:4`, `README.md:26`.

**6. Make the IDE-restart requirement impossible to miss (S)**
After the install wizard summary (`cli/install.js:1831–1841`), add a visible box or bold warning: "⚠ Reload your editor window now — commands won't appear until you do." Files: `cli/install.js:1101`.

## Kill your darlings

**The `rcode-seeded-not-configured` detection state in auto-init-guard** serves a real purpose (closing the "install defaults never confirmed" bug from #1034–#1036), but the mechanism — detecting the presence of a comment string in a config file — is fragile. If the install wizard ran and the user answered all questions, the config is NOT "not configured" — it's fully configured. The guard should distinguish "wizard ran" from "non-interactive install with defaults." The current approach over-triggers on every wizard-run install and forces redundant questions.

**The install wizard as a separate config layer from auto-init-guard** should be eliminated as a duplicate. There should be one place where users answer setup questions: the install wizard OR the auto-init-guard, not both. The install wizard is the better UX (runs in the terminal before the IDE is open, has a proper clack spinner). The inline auto-init-guard is a fallback. Currently they're peers and both fire.

**docs/getting-started.md "Common first workflows" section** (`docs/getting-started.md:90–112`) lists `/rcode-chain`, `/rcode-council`, `/rcode-discuss fatima`, and `/rcode-execute` as "first workflows." None of these will have useful output on an uninit'd project — they need a JOURNEY.md baseline first. This section should either be cut or moved to "Step 3 and beyond" with a prerequisite note.
